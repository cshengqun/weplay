## 一、现状盘点

### 1.1 已落地能力（截至 v1.15.1）

| 模块 | 能力 |
|---|---|
| 球局/报名/轮转/比分 | 同前：创建、在线报名（me 档案）、单打/双打/混双圆桌轮转、目标分与比分录入 |
| 结果信任（v1.14） | 多方确认状态机 `utils/confirm.js`；写操作全部收口 activity 云函数；activities 权限收紧 |
| 段位引擎（v1.15） | `utils/rank.js`：分项 ELO + 综合加权、定级赛、8 段段位与球王星级、确认后结算、历史回溯 backfill；rank 集合 `read:true / write:false`；全国段位榜 |
| 确认闭环（v1.15.1） | 48h 超时无异议自动确认结算（云函数定时触发器，每小时）；订阅消息骨架（`utils/notify.js`，模板 ID 待申请） |

### 1.2 现有数据模型（与本期相关）

- **rank 集合**：`{ _openid, name, avatar, elo:{singles,doubles,mixed}, counts:{singles,doubles,mixed}, combined, tier, tierName, played, placed, updatedAt }`
  - 注意：只有分项 **ELO 与场次数**，**没有分项胜/负、没有历史 ELO、没有成就**。
- **activities**：rotation.scores[key] 的确认 record 含 `status/required/confirmedBy/settled/autoConfirmed`；比赛对阵存于 `rounds[].matches[]`。
- **me 集合**：`{ _openid, nickname, avatar, gender, level, updatedAt }`。
- 客户端已有 `cloud.getNationalBoard()`（直读 rank）、`cloud.getRank(openid)`、`cloud.getAllActivities()`（分页拉全量，上限约 500 场）。

### 1.3 本期关键洞察：数据「算出来了，却没被看见」

1. **涨分反馈是断的**：确认后云函数静默结算 ELO，球友在比分页看不到「这场我 +12、升到金羽二段」——这是排位体系最强的即时正反馈钩子，目前完全没接到 UI。
2. **段位没有回流到约球主流程**：ELO 只在全国榜可见，报名名单、对阵表上看不到任何人的段位。段位应成为社交货币，并帮组织者合理分组。
3. **没有「人」的一页**：排行榜、报名名单点姓名仍是 `wx.showModal` 弹窗，看不到一个球员的分项战绩、曲线、成就、常用搭档。
4. **结算即覆盖**：rank 每次更新覆盖旧值，无法画成长曲线、无法算最高段位/连胜，也不支持误结算回滚。

> 结论：v1.16 的核心不是堆功能，而是**把已有的段位数据「可视化、可追溯、可分享」**，并顺手补上反馈断点。

## 二、v1.16 功能设计（每项含场景 / 价值 / 数据 / 思路 / 风险 / 优先级）

### F1. ELO 变更流水 `rating_log` 集合 — P0

- **目标用户/场景**：所有上榜球友；个人主页成长曲线、单场涨分、最高段位、误结算回滚都依赖它。
- **用户价值**：能看到「我是怎么一步步打上来的」，是成长感与信任的底座。
- **功能描述**：每次段位结算追加一条不可变流水。
- **数据结构（新增集合 `rating_log`，权限同 rank：`{"read": true, "write": false}`）**：
  ```
  { _openid, at, activityId, activityName, key, mode,
    before, after, delta, expected, combinedAfter, win, auto:false }
  ```
  - `expected`：该队员本场预期胜率（用于「爆冷」成就）；`win`：胜负；`auto`：是否超时自动确认结算。
- **实现思路**：
  - `rank.settleOne` 已返回 `[{openid, elo, delta}]`；在云函数 `settleConfirmedMatch` / `autoConfirmSweep` 结算后，批量 `add` 流水（可在同函数内顺序写，简单可靠）。
  - 业务幂等键 `{activityId, key, mode, _openid}`：写入前先 `where` 查一次，存在则跳过（确认/回溯重复触发不重复记账）。
  - `backfill` 全量回溯**默认不重写流水**（避免历史爆量）；老用户曲线从「v1.16 上线后」开始，提供一个带二次确认的「补建历史曲线」开关，按 activities 重放并幂等补写。
- **技术风险**：双打每场 4 人 = 4 条，量级 = 已结算场次数 × 上场人数，远小于 activities 体量，免费额度内无忧；批量写注意云函数超时（分批，每场结算量很小，无压力）。

### F2. 个人统计纯函数 `utils/stats.js` — P0

- **目标用户/场景**：个人主页、战报、成就都需要「某球员的聚合战绩」。
- **用户价值**：一处计算、处处复用；纯函数可单测，保证数字可信。
- **功能描述**：输入「活动列表 + openid」，输出该球员的完整画像。
- **建议接口（纯函数，node 可单测）**：
  ```
  buildPlayerStats(activities, openid) -> {
    byMode: { singles:{plays,wins,losses,winRate,setWon,setLost,net}, doubles:{...}, mixed:{...} },
    total:{plays,wins,losses,winRate},
    streak:{win, loss},            // 当前连胜/连败（按时间排序该球员已确认比赛）
    bestStreak: number,            // 历史最长连胜
    partners:[{openid,name,times,wins}],  // 常用搭档（双打/混双同队共现，取 Top5）
    rivals:[{openid,name,times,myWins}],  // 高频对手 + 交手胜负（苦主/福星）
    recent:[{at,activityName,mode,sA,sB,win,partnerNames,oppNames}] // 最近 N 场
  }
  ```
- **实现思路**：复用 `score.computeLeaderboard` 的遍历口径（只统计 `status=confirmed` 且非平分场次，与 ELO 结算口径一致）；双打/混双从 `matches` 的 teamA/teamB 反查同队（搭档）与对面（对手）。
- **技术风险**：需严格与 ELO 结算口径对齐（只算 confirmed、平分不计），否则会出现「战绩场次和段位场次对不上」的信任问题；以单测锁定口径。

### F3. 个人主页 `pages/profile/profile` — P0

- **目标用户/场景**：球友看自己/别人的羽毛球名片；从排行榜、报名名单、分享卡片进入。
- **用户价值**：段位、战绩、成长、成就的总载体，是留存与社交裂变支点。
- **页面信息架构（自上而下）**：
  1. **身份卡**：头像、昵称、段位徽章 + 星级/球王称号、综合 ELO、全国排名（rank 中的位次）、定级进度（未定级时）。
  2. **分项三卡**：单打/双打/混双 各显示 ELO、场次、胜-负、胜率、净分。
  3. **成长曲线**（F4）。
  4. **数据亮点**：当前连胜/连败、最长连胜、最高段位、常用搭档、苦主/福星（点头像可跳到对方主页）。
  5. **成就墙**（F5）。
  6. **最近比赛**（F7 战报入口）。
- **入口改造**：
  - `leaderboard`：榜单行与「我的段位卡」点击 → `navigateTo('/pages/profile/profile?openid=xx')`（替换现在的 `onNameTap` 弹窗；需让 `getNationalBoard` 返回 `_openid`）。
  - `join`：报名名单/对阵中带 openid 的球员点头像进主页；无 openid 的手动球员提示「暂未绑定，无段位档案」。
  - 分享：主页 `onShareAppMessage` 带 openid，他人点开看到同一名片。
- **数据获取（推荐分两阶段）**：
  - **v1.16 先用客户端聚合（快、免改云函数）**：`getRank(openid)` 拿段位 + `getAllActivities()` 拉活动 + `stats.buildPlayerStats` 现算 + `rating_log` 按 openid 查询画曲线；结果本地缓存（短 TTL，复用全国榜的缓存模式）。
  - **数据量上来后（活动 >300 或反馈慢）再上云函数 `getProfile`**：服务端聚合并可定时预计算「个人快照」，客户端一次取走。
- **降级**：未开通云开发/无 openid 时，主页只展示本机按姓名聚合的战绩（复用 score 口径），不显示段位。
- **技术风险**：首屏拉全量活动偏重 → 缓存 + 骨架屏 + 分段 setData；查他人主页只暴露比赛公开数据，不暴露性别等无关隐私。

### F4. 成长曲线 — P1

- **场景/价值**：把「变强」画出来，是最直观的留存钩子（对标羽 Rank「成长阶段」）。
- **功能描述**：综合 ELO 随场次/时间的折线；可切换单打/双打/混双；标注定级赛区间、段位分隔线、最高段位点。
- **数据/实现**：数据来自 `rating_log.combinedAfter`（分项曲线取 after）；用小程序 canvas 2d 自绘轻量折线（无第三方依赖）；点数过多按月/按场抽样。
- **风险**：canvas 多端（iOS/安卓/开发者工具）适配；MVP 可先用「分段折线 + 关键点数值」，不做复杂手势缩放。

### F5. 成就引擎 `utils/achievement.js` — P1

- **场景/价值**：覆盖排位之外的轻目标，结算后即时解锁形成正反馈；纯函数可单测。
- **接口**：`evaluate({ rank, stats, logs }) -> [{key,name,desc,icon,got,progress}]`。
- **首批成就（均基于当前可获得的数据，避免画饼）**：
  | key | 名称 | 判定 |
  |---|---|---|
  | placement | 初露锋芒 | 完成任一单项 5 场定级赛 |
  | first_win | 首胜 | 第 1 场确认胜 |
  | matches_10/50/100 | 百战不殆系列 | 总场次达 10/50/100 |
  | streak_3/5/10 | 连胜系列 | 最长连胜达 3/5/10 |
  | tier_jinyu/zuanshi/xingyao/qiuwang | 段位里程碑 | 最高综合段位达到金羽/钻石/星耀/球王 |
  | giant_killer | 巨人杀手 | 单场 expected<0.2 却获胜（爆冷，取 rating_log.expected） |
  | mode_specialist | 单项达人 | 某分项场次≥20 且胜率≥60% |
  | ironman | 全勤王 | 单场球局打满该类型全部轮次（由活动轮转数据判定） |
- **明确暂不做**：逆风翻盘、得分王等需要「逐球/每分过程数据」的成就——现仅录终场比分，数据不支持，列入远期。
- **风险**：成就解锁时机（结算后重算本人）；未读通知先不做红点，MVP 仅在主页置灰/点亮。

### F6. 结算涨分即时反馈 — P0（低成本高回报，建议优先于完整主页）

- **场景**：球友确认比分、或比赛被自动确认后，立刻看到自己这场 ELO ±N、段位/星级变化。
- **价值**：把排位最强的「上分」正反馈接到用户眼前；这是 v1.15 做完后最明显的体验断点。
- **功能描述**：
  - 云函数 `confirmMatch` 已返回 `changes`（结算 openid 列表），扩展为返回每人 `{openid, mode, delta, beforeTier, afterTier, placed}`（settleOne 结果 + 结算前后段位对比）。
  - 球友确认后弹「本场战报」浮层：胜负、ELO ±N（涨绿跌红）、段位进度条、是否升段/完成定级；组织者 schedule 页每场也显示参与者的涨分摘要。
  - 自动确认（48h）的场次，在球友下次打开 join 页时用 rating_log 未读标记补一次提示。
- **数据关系**：依赖 F1 rating_log 与现有 confirmMatch 返回；不改结算规则。
- **风险**：浮层不要打断批量确认，提供「知道了」且每场只弹一次（用 rating_log 去重）。

### F7. 战报分享卡片 — P1

- **场景/价值**：升段、爆冷、连胜后生成可分享图，低成本拉新。
- **功能描述（分两步）**：
  - MVP：结算浮层/主页提供样式化「战报卡」（头像、段位、本场 ±N、星级、二维码引导），用小程序原生卡片 + onShareAppMessage 分享即可。
  - 进阶：canvas 出长图保存相册（涉及小程序码生成，需云函数 `wxacode.getUnlimited`，后置）。
- **风险**：小程序码生成需发布后有线上页面；先做原生分享卡片，不阻塞。

### F8. 段位徽章回流约球主流程 — P1

- **场景**：报名名单、轮转对阵、战绩榜上，名字旁显示小段位徽章/颜色。
- **价值**：让段位在「打球现场」高频曝光（社交货币），并帮组织者按水平分组、生成更均衡的对阵。
- **实现**：rank 集合 `read:true`，join/schedule 页可批量按 openid 查段位（或随活动数据缓存一份快照）；用 `rank.starsOf` 出徽章文案；无档案显示「未定级」。
- **风险**：批量查询次数 → 一次活动人数有限（<30），按 openid `whereIn` 一次取回并缓存即可。

### F9. 无 OpenID 战绩认领 — P2（v1.16 可做轻量版）

- **场景**：组织者手动添加的老球员有比赛、影响他人 ELO，却没有自己的档案。
- **功能描述（轻量版）**：该球员用本人微信打开球局分享卡报名后，若姓名匹配且本人确认，提示「认领历史战绩」，把其历史手动记录按 openid 关联（沿用 score.computeTotal 已有的同名归并逻辑，增加 openid 绑定动作与云函数）。
- **风险**：冒认/重名 → 需组织者或本人二次确认，仅合并「同组织者/同姓名」记录；完整方案留待俱乐部体系。

## 五、本期 Top3 推荐

1. **F1 rating_log 变更流水 + F6 结算涨分即时反馈（合并为一个最小闭环先上）**
   理由：v1.15 最大的体验断点是「确认完不知道自己涨没涨分」。落一条流水、在确认后弹出战报，用最小改动把排位最强的正反馈接通，同时为曲线/成就/回滚铺好数据。建议作为 v1.16 的第一个可发布增量。

2. **F2 stats.js + F3 个人主页**
   理由：所有个人数据（分项战绩、连胜连败、常用搭档、苦主）需要一个可信的纯计算层和一个承载页；主页把排行榜/名单的姓名弹窗升级为可探索的球员名片，是留存与社交裂变支点。纯函数可单测、首期可纯客户端聚合，落地风险低。

3. **F8 段位徽章回流约球主流程**
   理由：成本很低（rank 已全员可读、starsOf 已就绪），却能让段位在报名/对阵/现场高频曝光，既强化社交货币，又帮组织者按水平均衡分组，直接服务「打一场好球」的核心场景。
