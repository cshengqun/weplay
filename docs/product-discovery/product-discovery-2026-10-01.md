# 产品功能探索报告 · 2026-10-01

> 本期主题：**补齐「赛中」这一环——现场实时计分、多人协作记分与 TV 大屏**。前几期已把「赛前」（报名/候补/签到，09-30）与「赛后」（段位/个人数据，09-29）规划清楚，但比赛**进行当中**怎么记分、怎么让全场看到比分，仍是空白：现在要组织者一个人手动填终场数字。本期把赛中体验做成可开工的设计。
>
> 报告人：产品经理（定时任务自动产出）｜项目：球局轮转 weplay（当前版本 **v1.15.1**）

## 一、现状与本期判断

### 1.1 进度核对

- 已上线：v1.14 信任地基、v1.15 段位引擎、v1.15.1 确认闭环。
- 已规划未动工：v1.16 个人数据中心（09-29）、v1.17 到场与组织效率（09-30）；仓库中暂无 profile/stats/achievement/signup/scoring 等模块。
- **赛中现状（`pages/schedule`）**：
  - 比分通过 `onScoreInput` 在输入框**手填两个终场数字**，没有逐球记录、没有局分、没有赛点/deuce 提示。
  - 录入权限只在组织者（云函数 `saveScore` 校验 `doc._openid`），**一个人要记全场所有场地的比分**。
  - 无横屏页、无投屏/大屏（全项目无 landscape/orientation 相关代码）。
  - record 只存 `{sA,sB,...}`，**没有比赛过程数据**——09-29 报告因此明确标注「逆风翻盘/得分王等成就数据不支持」。

### 1.2 核心判断：一场球的全流程，唯独「赛中」最薄

1. **记分是比赛日最高频、最不能错的操作**，却停留在「赛后回忆着填数字」，容易记错、引发争议（恰好打在 v1.14 确认机制要解决的信任问题上）。
2. **组织者负担过重**：多片场地同时打，一人录全场不现实；而场上队员最清楚比分，却没有自助记分入口。
3. **现场缺少「一块屏」**：下一轮谁上、当前比分、实时排名没有公开展示，仪式感和段位存在感弱（Play Engine 的 TV 模式已验证此需求）。
4. **逐球过程是高价值数据源头**：赛点、deuce、逆转、得分高潮都来自过程；有了它，09-29 个人数据中心里「做不了」的成就和战报才能解锁。

> 结论：赛中套件不是新赛道，而是把现有「轮转 → 比分 → 确认 → 段位」主链路在比赛当天真正跑顺，并为个人数据反哺过程素材。

## 二、核心设计：实时计分引擎 `utils/scoring.js`（纯函数，可单测）

与 `rotation.js / score.js / confirm.js / rank.js` 同一架构：规则全部收敛到纯函数，前端与云函数共用、node 单测锁定。

### 2.1 计分规则（羽毛球，可配置）

- 单局目标分 `target`（沿用现有 11 / 15 / 21 / 自定义）。
- 常规：先到 `target` 者胜。
- Deuce（平分加赛）：到达 `target-1` 平后，需**领先 2 分**获胜；设封顶分 `cap`，到 cap 即胜。
  - 建议默认：21 分制 `cap=30`（29 平后第 30 分胜）、11 分制 `cap=15`；15 分制各馆规则不一（常见 17，也有不封顶），**做成可配置，默认值待与真实球馆确认（待验证）**。
- 每球状态：`{ a, b, servingSide, finished, winner, deuce, matchPointSide }`。
- 双打发球轮换/左右站位规则复杂且易错，**MVP 不做站位计算**，发球方仅作可选记录（P2）。

### 2.2 建议接口

```
createGame(target, cap) -> gameState
tapPoint(game, side)        // 'A'|'B' 得分，返回新状态（含是否 deuce/赛点/结束）
undoPoint(game)             // 撤销上一球（可多步，防误触）
isMatchPoint(game, side)    // 该方再得一分即胜（含 cap 场景）
isFinished(game)            // 是否结束、胜者
gameStats(game)             // {maxRunA,maxRunB,deuce,leadChanges,...} 关键过程统计
```

- 纯函数不可变更新，边界用单测覆盖：20:19 赛点、20:20 进 deuce、21:21 不结束、29:29→30 结束、撤销不破坏结束判定等。

### 2.3 与现有数据/结算的关系（关键：不破坏口径）

- 实时计分结束后，仍只产出**终场 `sA/sB`**，复用现有 `cf.buildRecord → cloud.submitScore → 多方确认 → ELO 结算`，**ELO 与确认规则一行不改**。
- 逐球序列**不实时上云、不长期存储**（频率高、价值低、费调用）；仅在结束时提交终场，可选附带 `gameStats` 关键统计。
- 三局两胜（业余进阶）列为 **P2**：record 扩展 `games:[{a,b}...]`，ELO 仍只看整场胜负，向后兼容单局。

## 三、功能清单（场景 / 价值 / 数据 / 思路 / 风险 / 优先级）

### M1. 现场实时计分板 — P0

- **目标用户/场景**：记分者（组织者或队员）在场地边，逐球点按记录一场比赛。
- **用户价值**：不用赛后回忆填分；自动判 deuce/赛点/终场，杜绝「21 平了到底打多少」的争议；结束一键提交进入确认。
- **功能描述**：新增 `pages/scoring/scoring`（参数 `id/type/key`，建议支持横屏）。大号「A 得分 / B 得分」按钮、撤销、当前局大比分、赛点/deuce 高亮、队伍名与头像；结束时二次确认并自动填入该场比分。
- **数据关系**：读 activity 拿对阵与 targetScore；写仍走 `submitScore`；record 可选新增 `stats`（过程统计）与 `scorerOpenid`（= 现有 submittedBy，复用）。
- **技术风险**：边打边记可能中途退出 → 本地暂存（wx.storage 按 key 草稿）；误触改分 → undo + 结束确认；与手动录入并存（手填入口保留作降级）。

### M2. 多人协作记分（队员自助记分） — P1

- **场景**：多片场地同时开打，组织者顾不过来；场上队员自己记自己那场。
- **用户价值**：记分责任分散到最清楚比分的人，组织者从「全场书记员」解放。
- **功能描述 / 权限改动**：云函数 `saveScore` 鉴权由「仅组织者」放宽为「**组织者 OR 本场带 openid 的参与者**」；参与者提交同样走 `buildRecord`（required 自动排除提交者本人），进入 v1.14 既有待确认流，相关方确认后才生效。
- **并发与防作弊**：
  - 已 `confirmed/settled` 的场次不可改（现有锁定已具备）；
  - `pending` 且尚无人确认时，记分员可修正自己提交的比分；一旦有人确认即锁定修改，需走异议；
  - 云函数串行写 + 状态机，避免多人覆盖；非组织者/非参与者提交一律拒绝。
- **数据关系**：复用 record 的 `submittedBy/required/confirmedBy/dispute`，**几乎不加字段**；仅放开鉴权与入口（join 页参与者场次出现「记分」按钮）。
- **风险**：熟人场景可能嫌确认麻烦——已有 48h 超时自动确认兜底（v1.15.1）。

### M3. TV / 投屏展示模式 — P1

- **场景**：球馆电视/投影或一台常开平板，公开展示当前轮次对阵、实时比分、积分榜与段位。
- **用户价值**：现场仪式感、「下一场谁上哪片场」一目了然、段位/榜单高频曝光（社交货币）。
- **功能描述**：新增横屏页 `pages/screen/screen?id=cloudId`（页面 json 设 `pageOrientation: "landscape"`）：
  - 顶部球局名 + 当前轮；按场地分卡显示对阵与比分；
  - 已完场显示终场比分与胜方；底部滚动积分榜/段位；
  - 定时（如 15~30 秒）拉取云端 activity 刷新（`getActivity` 已有），支持手动刷新。
- **数据关系**：纯读 activity + rank，无新写权限；可复用 schedule 的对阵/战绩解析逻辑。
- **技术风险/边界（需明确告知用户，待验证）**：小程序**不能直接在智能电视浏览器打开**；落地方式是「一台手机/平板常开该横屏页 + 屏幕镜像/AirPlay/HDMI 投屏到电视」。实时比分上云若只在终场提交，则大屏的「进行中比分」会滞后——若要强实时，需把当前场比分节流上云（建议每得分或每 5 秒写一个 `live` 草稿字段），列为 P1 可选项，评估云调用量后开启。

### M4. 比赛过程统计沉淀 — P2

- **场景/价值**：记录 deuce、最大连续得分、领先交替/逆转等关键统计，解锁 09-29 中标注「数据不支持」的成就（逆风翻盘、赛点之王、得分高潮）与战报素材。
- **功能描述**：`scoring.gameStats` 在结束时产出少量关键指标，随 record 存 `stats`（**不存逐球序列**，控制体量）；个人数据中心（v1.16）与成就引擎读取。
- **风险**：仅当使用实时计分板的场次才有过程数据，手填场次无——需在成就口径上区分或不强制。

### M5. 现场轮次/上场提醒 — P2

- **场景**：球友不知道自己下一场何时上、去哪片场。
- **功能描述**：大屏高亮当前/下一轮上场名单（M3 已含大半）；可选在每轮开始时由组织者一键触发订阅消息（复用 v1.15.1 `notify`，新增 `nextRound` 模板位），未申请模板前降级为大屏提示。

### M6. 三局两胜 / 正式赛制 — P2（与 v1.21 赛事合并考虑）

- 三局两胜、换边、间歇（11 分技术暂停）等正式规则；record 扩展 `games` 数组。复杂度较高、业余圆桌玩法以单局为主，建议并入后续「赛事赛制（小组赛+淘汰赛）」迭代统一设计，不在本期。

## 四、与现有链路 / 排位体系的关系

- **全链路定位**：签到（v1.17）确定上场名单 → 轮转生成 → **实时计分（M1）/协作记分（M2）/大屏（M3）** → 多方确认（v1.14）→ 超时兜底（v1.15.1）→ ELO 结算（v1.15）→ 个人数据与成就（v1.16，消费 M4 过程统计）。赛中是把这条链在现场跑顺的关键一环。
- **不改排位规则**：实时计分只改变「比分如何产生」，不改变「比分如何确认与结算」；全国榜 ELO、段位、定级、防刷（确认才计分、碾压低收益）维持现状。
- **对防刷的正向作用**：逐球记录 + 多人协作 + 多方确认，使伪造比分比「手填一个数字」难得多，过程统计也为后续异常检测（如大量 21:0）提供信号。
- **地区榜**：仍按 09-30 结论后置（密度依赖），本期不改动；现场大屏可先展示全国段位，为未来地区称号预留展示位。

## 六、本期 Top3 推荐

1. **M1 现场实时计分板（含 `utils/scoring.js` 计分引擎）**
   理由：记分是比赛日最高频且最不能错的动作，当前却靠赛后手填终场数字，是主链路体验最薄处。逐球点按 + 自动 deuce/赛点/终场判定，既当场消除比分争议（强化 v1.14 信任），又产出过程数据；纯函数可单测、提交仍走现有确认结算，落地风险低，是本期地基。

2. **M2 多人协作记分（放开 `saveScore` 给参与者）**
   理由：多片场地并行时，组织者一人记全场必然漏记错记。让场上队员自助记分、复用现成的多方确认与超时兜底做约束，几乎不加数据结构就能把记分责任去中心化，是性价比极高的一环。

3. **M3 TV 横屏大屏**
   理由：纯读、不改数据、开发量可控，却显著提升现场体验（谁上哪片场、实时比分、排名）与段位的仪式感/曝光度，是球馆场景的刚需展示位；需向用户说明落地方式为「平板/手机横屏 + 屏幕镜像」。

## 附：待验证事项

- 15 分制的 deuce 封顶分各馆不一（17 / 21 / 不封顶），默认 cap 需实测后确定，建议做成可配置。
- TV 大屏的「实时进行中比分」是否需要实时上云（live 草稿字段）及其云函数调用量，需按场地数与得分频率评估；MVP 可先只轮询终场。
- 小程序横屏页在 iOS/安卓/开发者工具的 `pageOrientation` 与投屏（屏幕镜像）兼容性需真机验证。
- 多人同时提交同一场比分的并发覆盖，需在云函数用状态机 + 「有人确认即锁定」实测。
- 双打发球轮换/站位、三局两胜、技术暂停等正式规则本期不做，留待 v1.21 赛事迭代。
- v1.16 / v1.17 蓝图均已就绪但尚未动工，建议尽快排期；本期 v1.18 与之相对独立，可并行开发。
