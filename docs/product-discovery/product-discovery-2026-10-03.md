# 产品功能探索报告 · 2026-10-03

> 本期主题：**从「一场球」到「一个组织」——俱乐部 / 球队容器开工蓝图**。前几期已把单场球的赛前（v1.17）、赛中（v1.18）、赛后（v1.16）与冷启动增长（10-02）规划完整，但这些都停留在「一次性球局」。本期设计把固定球友沉淀为长期组织的俱乐部层：它是留存与复办的容器、冷启动期密度无关的「身边榜」载体，也是未来赛事与商业化的基础。
>
> 报告人：产品经理（定时任务自动产出）｜项目：球局轮转 weplay（当前版本 **v1.15.1**，仓库中无任何 club 相关代码）

---

## 一、现状与本期判断

1. **球局是「点状」的，缺少「面」的沉淀**：一群固定球友每周打球，在产品里却只是一次次互相独立的 activities，没有统一主页、没有成员关系、没有「我们这群人」的榜和历史。组织者复办要重新凑人、新人无法了解这个群体。
2. **俱乐部是冷启动期就成立的功能**：与依赖全网密度的地区榜/约球广场不同，**一个 10 人固定球群就能用俱乐部**（内部榜、固定模板、成员沉淀），不依赖陌生人，符合 10-02「先做密度无关功能」的结论。
3. **它直接服务北极星（复办率）**：俱乐部主页的「再来一场」、固定模板、成员一键通知，把每周复办成本降到最低。
4. **它是「身边榜」的天然落地**：10-02 提出空窗期用身边榜替代全国榜竞争感，俱乐部内部榜正是最自然的身边榜。
5. **是后续能力的地基**：v1.21 小组赛/淘汰赛以俱乐部为组织单位；场馆导流、装备等商业化也以俱乐部为采购主体。

> 边界：俱乐部是**可选容器**，不建俱乐部的用户照常发起单场球，主流程零影响；本期不做陌生人「发现广场」（密度型，留 v2.0）。

## 二、关键设计决策：俱乐部内部榜不另起一套 ELO

这是本期最重要、最容易做复杂的决策。

- **方案 A（不采用）**：每个俱乐部独立算一套 ELO。问题：一场俱乐部球局要同时结算全国分与俱乐部分，双套结算链；俱乐部内比赛少时分数剧烈波动；实现与回溯成本高。
- **方案 B（推荐，MVP）**：俱乐部球局**照常走全国 ELO 结算**（确认/超时/防刷规则完全不变），俱乐部页只做两件事——
  1. 展示每个成员的**全国段位徽章与综合 ELO**（直接读 rank 集合）；
  2. 聚合该成员在**本俱乐部球局内**的场次/胜场/胜率（复用 `score.computeTotal`，按 `activity.clubId` 过滤）。
  排序默认按全国综合 ELO（跨场可比、更公平），提供「本俱乐部胜率」切换。
- **方案 C（P2 增强）**：俱乐部「战力分」＝近 30 天活跃度 + 胜率加权，作为 v1.20 地区战力分的本地化预演，不影响段位。
- 收益：**不新增任何结算链**，俱乐部只是给 activities 打了一个 `clubId` 标签 + 一层成员关系，风险与工作量都可控。

## 三、数据模型（新增集合，云函数写入）

### 3.1 `clubs`（权限 `{"read": true, "write": false}`，写走云函数）

```
{ _id, _openid(创建者/owner), name, logo(fileID), announcement,
  joinPolicy: 'open' | 'approve',      // 开放加入 / 需审核
  defaultActivity: { type, courts, targetScore, durationHours, startTime, venue, courtText },
  memberCount, status: 'active', createdAt, updatedAt }
```

### 3.2 `club_members`（权限同上；建议联合唯一 {clubId,_openid}）

```
{ clubId, _openid, name, avatar,
  role: 'owner' | 'admin' | 'member',
  state: 'active' | 'pending',          // approve 政策下的待审核
  joinedAt, title }                     // 可选昵称头衔
```

### 3.3 现有集合的最小改动

- **activities 增加可选 `clubId`**（缺省＝个人球局）；`cloud.cleanData` 白名单放行该字段。
- **预留 `tournamentId`**（v1.21 赛事用，本期不实现、不暴露入口）。
- me / rank / 确认 / ELO 结算逻辑**不改**。

## 四、功能清单（场景 / 价值 / 数据 / 思路 / 风险 / 优先级）

### C1. 创建俱乐部与基础资料 — P0

- **场景**：固定球群的组织者把「我们这群人」建成俱乐部。
- **价值**：一次性建立组织身份，后续球局、成员、榜单都挂在其下。
- **功能描述**：俱乐部名（必填）、队标（可选，复用 `uploadAvatar` 的图片上传）、公告、加入政策；创建者自动成为 owner。
- **数据/思路**：云函数 `club.create`（getWXContext 取 openid），事务式写 clubs + 一条 owner member；客户端「我的」页入口。
- **风险**：每人创建数量做软上限（待验证，如 5 个）防垃圾；名称合规走小程序内容安全（可后置，先长度/空值校验）。

### C2. 邀请与加入（分享卡 / 小程序码） — P0

- **场景**：组织者把俱乐部分享到微信群，球友点开即加入。
- **价值**：拉新与成员沉淀一步完成，复用小程序最成熟的分享链路。
- **功能描述**：俱乐部页 `onShareAppMessage` 带 `clubId`（路径 `pages/club/club?id=xx`）；未加入者看到「加入」按钮；`open` 直接加入，`approve` 进入 pending 由管理员审核；成员可主动退出。
- **数据/思路**：云函数 `club.join / approve / reject / leave`，按 `{clubId,_openid}` 去重；可选生成俱乐部小程序码（`wxacode`，需线上环境，P1）。
- **风险**：重复加入、已退出再加入的状态处理；审核流 MVP 可先只做 `open`，`approve` 置 P1。

### C3. 成员与角色权限 — P0

- **角色**：owner（创建者，唯一，可转让）、admin（可审核/发俱乐部球局/改公告/移除普通成员）、member。
- **功能**：成员列表、角色标识、管理员移除成员（不能踢 owner/同级）、owner 转让与解散（解散需二次确认，俱乐部球局数据保留但脱钩）。
- **数据/思路**：云函数 `club.kick / setRole / transfer / disband`，服务端逐项鉴权。
- **风险**：权限矩阵要在云函数严格判定，客户端按钮仅作展示；owner 离场须先转让或解散，避免无主组织。

### C4. 俱乐部主页 `pages/club/club` — P0

- **信息架构（页内分段或顶部 tab）**：
  1. 概览：队标、名称、公告、成员数、主场馆、「开一场球」「加入/已加入」；
  2. 球局：本俱乐部的球局列表（activities where clubId），含「再来一场」；
  3. 成员：头像墙、角色、段位徽章（点人进 v1.16 个人主页）；
  4. 内部榜：见 C5。
- **入口**：「我的」页（10-02 N3）的「我的俱乐部」、首页、分享卡；**不新增 tabBar**（加入「我的」后仍为 4 个 tab）。
- **风险**：纯读为主，复用现有列表加载与分页；无云开发时俱乐部不可用，需明确提示。

### C5. 俱乐部内部榜（方案 B） — P1

- **场景/价值**：固定球友间的即时竞争与谈资，冷启动期密度无关，是比全国空榜更强的留存钩子。
- **功能描述**：成员行显示全国段位徽章 + 综合 ELO + 本俱乐部「场次/胜场/胜率」；默认按综合 ELO 排序，可切「俱乐部胜率/场次」；顶部显示俱乐部整体段位分布（多少金羽/钻石…）。
- **数据/思路（MVP 客户端聚合，与 09-29 个人主页同策略）**：
  - `club_members where clubId` 取成员 openid；
  - `activities where clubId`（getAllActivities 增加 clubId 过滤）取球局；
  - `rank where _openid in 成员` 批量取段位；
  - 用 `score.computeTotal` 聚合俱乐部内战绩；结果短 TTL 缓存。
  - 数据量增大后再上云函数 `club.board` 预聚合。
- **风险/口径**：俱乐部内战绩只统计 `confirmed` 场次（与 ELO 一致）；无段位成员（未定级）排在有段位之后并标注「定级中」。

### C6. 俱乐部球局与固定模板 / 周期开球 — P1

- **场景**：俱乐部每周固定时间场地打球，复办不应重填。
- **功能描述**：
  - 俱乐部 `defaultActivity` 保存常打配置（类型/场地数/目标分/时长/时间/场馆）；主页「开一场」一键预填进入 create 页，新球局自动带 `clubId`；
  - 球局结束页/俱乐部主页「再来一场」（与 10-02 N2 模板复用同一能力，俱乐部提供默认值）；
  - 可选「每周固定球局」提醒（订阅消息 `remind`，到点提醒管理员开球，不自动创建）。
- **权限**：MVP 仅 owner/admin 能发带 clubId 的俱乐部球局（防陌生人借俱乐部名义）；普通成员可发个人球局。是否放开给全体成员，做成俱乐部开关（待验证）。
- **风险**：俱乐部球局与个人球局在创建/列表/分享上要清晰区分（显示俱乐部名+队标）。

### C7. 俱乐部数据统计 — P2

出勤率（报名/签到比，依赖 v1.17 签到）、活跃成员、主场馆、近期场次趋势；纯聚合展示，增强组织粘性，待签到上线后做。

### C8. 多俱乐部与身份 — P1

- 一个 openid 可加入多个俱乐部；「我的俱乐部」列表切换；发起球局时选择归属「个人 / 某俱乐部」；个人主页（v1.16）展示其所属俱乐部队标。
- **风险**：球局归属唯一（一个球局至多一个 clubId）；成员在不同俱乐部战绩独立聚合，全国 ELO 唯一。

### C9. 赛事预留（不在本期实现） — P2

俱乐部是 v1.21 小组赛/淘汰赛的组织单位；本期仅在 activities 预留 `tournamentId`、clubs 不做赛事 UI，避免提前复杂化。

## 五、云函数与权限矩阵

建议新增独立云函数 `cloudfunctions/club/index.js`（与 activity 同模式，getWXContext 鉴权）；读尽量客户端直读（两集合 read:true），写全部走云函数：

| action | 鉴权 | 说明 |
|---|---|---|
| create/updateProfile | 任意人创建；owner/admin 改资料 | 含默认模板、公告、加入政策 |
| join | 任意登录用户 | open 直接 active；approve 写 pending；联合去重 |
| approve/reject | owner/admin | 审核 pending |
| leave | 本人 | 退出；owner 须先转让/解散 |
| kick/setRole/transfer/disband | owner（kick 可 admin） | 严格服务端鉴权 |
| board（P2） | 公开读 | 数据量大后的内部榜预聚合 |

俱乐部球局的创建/比分/确认/结算仍走现有 activity 云函数，仅在创建数据中携带 `clubId`（服务端校验调用者为该俱乐部成员/管理员）。

## 六、与排位体系的关系（重点章节）

- **全国榜（已上线）**：规则不变。俱乐部球局与个人球局一视同仁，全部走「多方确认/超时兜底 → ELO 结算 → rank」，俱乐部**不产生独立 ELO、不成为法外之地**，因此不引入新的刷分通道。
- **俱乐部内部榜（本期新增，方案 B）**：全国段位 + 俱乐部内战绩的聚合视图，不参与升降级计算；排序与切换规则见 C5。它解决的是全国榜空窗期「身边没有竞争感」的问题。
- **地区榜（v1.20，仍后置）**：俱乐部可作为地区战力的聚合单元（某城市的俱乐部实力榜），但需密度达标后开放；俱乐部资料里的地区字段本期不强制采集，沿用 v1.17 场馆定位预埋。
- **赛季（v1.20）**：俱乐部内部榜可在赛季末产出「赛季俱乐部排名/最佳进步成员」，数据依赖 rating_log（v1.16）与 clubId，本期只预留。
- **防刷**：内部榜不改变结算门槛；若出现刻意刷俱乐部胜率，因排序主轴是全国 ELO（受确认与预期胜率约束），刷俱乐部胜场对段位无帮助，动机有限。

## 七、冷启动与降级

- 俱乐部完全可选：不建俱乐部，发起/报名/轮转/记分/段位全部照常。
- 未开通云开发：俱乐部为纯云端能力，入口置灰并给开通指引（沿用现有降级文案）。
- 不做陌生人「发现/广场」：本期只能通过分享卡/小程序码加入已知俱乐部，避免冷启动期空列表与陌生人安全问题；发现能力留 v2.0。
- 上线节奏建议：先让种子组织者（你自己的固定球群）建 1 个俱乐部跑通「建群→邀请→开俱乐部球局→内部榜→再来一场」，再放开。

## 九、本期 Top3 推荐

1. **俱乐部最小可用闭环（C1 创建 + C2 邀请加入 + C3 权限 + C4 主页）**
   理由：这是把点状球局沉淀为长期组织的最小集合，也是其余俱乐部功能的地基；云函数鉴权与现有 activity 同模式、数据模型简单（两集合 + activity 一个字段），单群即可验证，不依赖全网密度。

2. **俱乐部内部榜（C5，方案 B：全国段位 + 俱乐部内战绩聚合）**
   理由：冷启动期全国榜稀疏，固定球友间的内部排名才是即时、可持续的竞争与谈资；关键是不另起一套 ELO、不新增结算链，只复用现成 rank 与 score 聚合，工作量小而留存价值高，是俱乐部上线后用户最先感知的亮点。

3. **俱乐部固定模板 /「再来一场」（C6，与 v1.17 模板能力合并建设）**
   理由：直接作用于北极星「复办率」——固定球局每周配置相同，一键套用并自动带 clubId、可通知原班人马，把组织者每周的重复劳动降到最低；与 10-02 的 N2 是同一能力，俱乐部只是提供默认模板，边际成本低。
