## 二、本期关键洞察：段位链路有一个会"卡死"的断点

v1.15 把"结算"严格绑定在**全部相关方确认**上，这在公平性上正确，但当前缺少两个配套，导致真实使用中比赛极易**永远停在 pending、段位不结算**：

1. **没有任何通知**：组织者录入比分后，球友不知道有比赛待确认；球友提出异议后，组织者也不知道。代码中无 `requestSubscribeMessage` / 订阅消息。
2. **没有超时兜底**：09-25 报告设计过"48 小时未确认自动生效"，**未实现**。只要有一个球友忘记/不打开小程序，这场比赛（及同场其他人的段位）就一直挂起。

> 结论：**通知 + 超时自动生效不是锦上添花，是 v1.15 段位体系能否真正跑起来的前提。** 建议作为最优先的链路补丁。

### 其他新暴露的缺口（v1.15 后）

3. **ELO 没有历史**：rank 文档每次结算直接覆盖，无 ELO 变化记录 → 成长曲线、"这场我涨了多少分"、最高段位都无法呈现。
4. **rank 只有分项 counts（场次数），没有分项胜负**：分项胜率/净分仍需临时从 activities 计算。
5. **个人主页缺失**：段位、分项 ELO 没有展示页；排行榜点姓名仍是 `wx.showModal` 弹窗，无法探索一个球员。
6. **锁定后无纠错出口**：settled 比赛组织者不能改、不能异议；若比分确实记错，目前没有作废/回滚/申诉通道。
7. **无 OpenID 球员（手动名单）无段位**：他们的比赛用估算 ELO 影响队友结算，但本人不进榜，也没有"认领战绩"引导。
8. **单机模式无段位**：段位仅云端产生，需在产品上明确告知，避免单机用户困惑。

## 三、重点设计一：确认闭环补丁（P0，段位链路的热修）

### 3.1 订阅消息提醒

- **触发点与模板**（模板需在小程序后台「订阅消息」申请，**本人操作**）：
  | 场景 | 通知对象 | 内容（建议） |
  |---|---|---|
  | 组织者录入比分 | 待确认球友 | 「你有 N 场比赛待确认，点击核对」 |
  | 球友提异议 | 组织者 | 「XX 对某场比分有异议：原因」 |
  | 全部确认、段位结算 | 上场球友 | 「比赛已确认，你的段位变为 XX，ELO ±N」 |
- **授权方式**：组织者录入/球友报名成功后调 `wx.requestSubscribeMessage` 一次性授权（一次授权对应一次发送）；长期模板需审核，建议先用一次性模板。
- **发送在云函数**：settleConfirmedMatch / disputeMatch / saveScore 内用 `cloud.openapi.subscribeMessage.send`（需云函数具备 openapi 调用权限）。
- 风险：一次性模板授权率低 → 配合下面的超时兜底，不把链路完全押在通知上。

### 3.2 超时自动生效（定时触发器）

- activity 云函数增加**定时触发器**（`config.json` 配 `timer`，如每小时跑一次），或独立小云函数：
  - 扫描近 N 天活动中 `status=pending` 且录入时间超过 **48 小时**的 record；
  - 对"无人提出异议"的场次，自动补齐所有 required 确认（标记 `autoConfirmed:true`）→ 触发结算；
  - 有异议的不自动生效，继续挂起并提醒组织者。
- 自动生效后仍保留**申诉窗口**（如 7 天内可由参与者申诉，复核后回滚）。
- 时长 48h 为建议初值，需小范围实测（09-25 已标待验证）。

### 3.3 锁定后的纠错通道（P1）

- 云函数新增 `adminResetMatch`：仅**管理员 OpenID 白名单**可调用，对误记的 settled 场次：
  1. 标记该场作废（record.invalid=true）；
  2. 依据 rating_log（见 4.1）反向冲销该场 ELO；
  3. 重新开放组织者改比分、重新确认结算。
- MVP 可先只做"作废 + 重新回溯 backfill"（backfill 已能全量重建，实现成本低）。

## 四、重点设计二：个人数据中心（v1.16 主体）

### 4.1 ELO 历史快照（成长曲线的数据底座）

- 推荐**独立集合 `rating_log`**（与 rank 解耦、可分页、榜单查询不被大数组拖累）：
  `{ _openid, at, activityId, key, mode, before, after, delta, combinedAfter }`
- 每次结算（settleConfirmedMatch）在写 rank 后，为每个有 OpenID 队员 add 一条。
- 权限同 rank：`{"read": true, "write": false}`。
- 用途：成长曲线（combinedAfter 随时间）、单场 ELO 变化、最高段位回溯、结算回滚（配合 3.3）。
- 备选：rank 内嵌 ratingHistory 数组（实现简单但不利榜单流量与分页），数据量小可作过渡。

### 4.2 个人主页信息架构（新页面 pages/profile/profile）

入口：排行榜点姓名/头像进入（替代弹窗）、首页"我的"入口、分享卡片。

```
┌ 顶部身份卡：头像、昵称、段位徽章 + 星级、综合 ELO、全国排名
├ 分项卡（单打 / 双打 / 混双）：分项 ELO、定级进度、场次、胜、负、胜率、净分
├ 成长曲线：综合 ELO 随时间走势（rating_log）
├ 数据亮点：当前连胜/连败、最高段位、常用搭档、苦主/福星（交手记录）
├ 成就墙：已获得徽章（achievement 引擎）
└ 最近比赛：可点进战报卡片（对阵、比分、ELO 变化、可分享）
```

- **数据聚合走云函数**：新增 action `getProfile`（参数 openid，可查他人）：
  1. 读 rank（段位/分项 ELO/counts）；
  2. 遍历 activities，按 mode 用 score.computeLeaderboard 聚合该 openid **分项战绩**；
  3. 双打/混双统计**搭档/对手共现频次**、按时间算**连胜连败**；
  4. 读 rating_log 画曲线、取最近比赛；
  5. 跑 achievement 引擎得成就。
  - 结果做短 TTL 缓存（如 10 分钟），降低重复计算。
- 客户端渲染，复用 leaderboard 段位配色；曲线用轻量 canvas 或折线组件。
- 风险：每次聚合遍历 activities 有成本 → 云函数侧缓存 + 分页 + 上限 500 场，数据量上来后改为异步预计算（定时刷新个人快照）。

### 4.3 成就引擎 utils/achievement.js（纯函数 + 单测）

- 输入个人统计 + rating_log，输出 `[{key,name,desc,got}]`，可单测。
- 首批成就（覆盖排位之外的轻目标）：
  - 场次类：初来乍到、10 / 50 / 100 场
  - 胜负类：首胜、3 / 5 / 10 连胜、终结者（击败高自己 ≥200 ELO 者）、逆风翻盘（低分逆转）
  - 分项类：单打王、双打万金油、混双达人
  - 段位类：晋身金羽 / 钻石 / 星耀 / 球王
  - 活跃类：全勤王、赛季 N 场
- 成就解锁可在结算后顺带计算并通知（订阅消息），形成即时正反馈。

### 4.4 比赛历史与战报卡片（P1）

- 个人维度比赛列表（rating_log + activities），每场展示对阵、比分、搭档/对手、ELO ±。
- 生成可分享的"战报卡片"（canvas 出图），是低成本社交裂变素材。

## 七、本期 Top3 推荐

1. **确认闭环热修：订阅消息 + 48h 超时自动生效（v1.15.1）**
   理由：v1.15 的段位结算严格依赖全部确认，但当前零通知、零兜底，任何一个球友不确认，整场段位就永久挂起。这是段位体系真正跑通的前提，属不可跳过的 P0。

2. **个人数据中心主页（pages/profile，v1.16 主体）**
   理由：段位、分项 ELO、战绩、成长、成就都需要一个"人"的页面承载；它把排行榜的姓名弹窗升级为可探索的球员主页，是留存与社交裂变的支点。

3. **rating_log ELO 历史 + 成就引擎**
   理由：成长曲线和"这场涨了多少分"依赖历史快照（当前结算即覆盖，无法回溯）；成就引擎以低成本提供排位之外的轻目标，并在结算后即时反馈，二者共同把"变强"可视化、可分享。
