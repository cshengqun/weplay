# 产品功能探索报告 · 2026-09-30

> 本期主题：**「办好每一场球」——到场确定性与组织效率套件**。段位/个人主页解决的是「赛后」的成长价值；而约球真正高频的痛点在「赛前与现场」：放鸽子、满员、临时换人、收钱记账。本期把这条主线做成可开工的设计，并据此重排路线图。
>
> 报告人：产品经理（定时任务自动产出）｜项目：球局轮转 weplay（当前版本 **v1.15.1**）

---

## 一、现状与本期判断

### 1.1 进度核对

- 已上线：v1.14 信任地基、v1.15 段位引擎、v1.15.1 确认闭环（48h 超时自动确认 + 订阅消息骨架）。
- **v1.16 个人数据中心蓝图已就绪（见 09-29 报告）但尚未动工**：仓库中暂无 `pages/profile`、`utils/stats.js`、`utils/achievement.js`、`rating_log` 相关代码。
- 报名侧现状（`pages/create`、云函数 `join`）：
  - `player` 只有 `{id,name,gender,level,avatar,openid,createdAt}`，**没有任何状态字段**——报名即正式，无请假/候补/签到。
  - 球友**只能报名、不能自助取消**（云函数只有 `join`，没有 `leave`），不来只能让组织者手动删除。
  - 球局**无人数上限**，自然也没有候补；无签到；无费用；场馆只有 `venue/courtText` 两段文本。

### 1.2 核心判断：排位是「赛后价值」，组织效率是「能不能打成」

1. **到场不确定是约球第一痛点**：业余球局鸽子率高，一个人不来，双打轮转/混双人数立刻失衡，组织者要现场重新数人、改阵。当前产品把「报名名单」直接当作「上场名单」，没有任何校验环节。
2. **组织杂务没有被承接**：场地费 AA、谁交钱了，普遍还在群里发红包 + 手动记账，是组织者每场必做的苦活。
3. **冷启动现实要求调整优先级**：地区榜、约球广场依赖**用户密度**（一个城市没几百人，地区榜就是空的）；而请假/候补/签到/记账在**单个球群、单场球**里立刻有用，且能让「真的上场的人」更准——反过来喂养 ELO 数据质量。
4. 结论：**组织效率套件应提前到与个人数据中心相邻的位置，地区榜后置**（地区字段可低成本预埋）。

## 二、统一设计：报名状态机（G1/G2/G3 的共同地基）

候补、请假、签到都在改「一个报名者的状态」，应先建统一状态机，避免做成三个零散开关。建议新增纯函数 `utils/signup.js`（可单测，前端与云函数共用，与 `confirm.js` 同模式）。

### 2.1 数据模型变更

- **activity 新增**：
  - `capacity`：人数上限（0 或缺省 = 不限）。
  - `checkInOpen`：组织者是否已开启签到（布尔）。
- **player 新增字段**（老数据缺省即视为 `signed`、未签到，向后兼容）：
  ```
  state: 'signed' | 'waitlist' | 'leave'   // 默认 signed
  waitlistSeq: Number                       // 候补序号（signed 为 0）
  checkIn: Boolean                          // 是否到场签到
  leaveAt, leaveReason
  checkInAt
  ```

### 2.2 状态流转

```
报名 join
  ├─ 正式名额未满（signed 数 < capacity，或不限）→ signed
  └─ 已满 → waitlist（waitlistSeq 递增，显示"候补第 N 位"）

signed 请假 leave（开赛前允许）
  → leave；同时触发候补递补：waitlist 队首 → signed
  → 订阅消息通知被递补者（复用 v1.15.1 notify，新增一个模板位）

开启签到 checkInOpen（组织者，建议开场前 30 分钟）
  → 球友在 join 页一键"我到了" checkIn；组织者可代签/撤销
生成轮转
  → 默认只使用 state=signed 且 checkIn=true 的人（组织者可手动勾选调整）
```

- **截止规则**：进入「已生成轮转 / 已开赛」后锁定请假（与现有「确认轮转后不能重新生成」的锁定语义一致），现场离场走 G4 临时换人/弃权。
- **候补递补策略**：MVP 采用「自动递补 + 订阅通知」，不强制候补者二次确认（降低复杂度）；被递补者若不来，由组织者在签到阶段处理。后续可加「N 分钟未确认顺延下一位」。
- **容量与混双/场地的关系**：capacity 是「报名人数上限」，与轮转所需人数（双打 4 人、混双男女配比）解耦；仅控制报名，不改轮转算法。

### 2.3 云函数改造（activity/index.js，沿用服务端鉴权）

| action | 鉴权 | 作用 |
|---|---|---|
| `join`（改造） | 任何人 | 按 capacity 决定写入 `signed` 或 `waitlist` |
| `leave`（新增） | 本人 openid 匹配该 player | 自助请假；触发候补递补；手动名单（无 openid）只能组织者删 |
| `checkIn`（新增） | 本人 | 仅 `checkInOpen` 后可签到；幂等 |
| `setCheckIn`（新增） | 组织者 | 开关签到、代签/撤销某人 |
| `setCapacity`（新增） | 组织者 | 设置人数上限（也可直接并入现有 `updateMeta` 白名单） |

均走现有 `callActivity`，客户端 `utils/cloud.js` 增加对应封装。

## 三、功能清单（每项含场景 / 价值 / 数据 / 思路 / 风险 / 优先级）

### G1. 球友自助请假 / 取消报名 — P0

- **场景**：报名后临时来不了，现在只能群里说一声、等组织者删，容易漏。
- **价值**：把组织者从「人工登记鸽子」中解放出来；候补能立刻顶上，直接提升成局率。
- **数据/思路**：player `state='leave'` + `leaveAt/reason`；云函数 `leave`；join 页对本人已报名的状态显示「取消报名 / 请假」按钮；组织者名单标注「已请假」。
- **风险**：开赛后请假要锁定；与已生成轮转的冲突（已进对阵的人请假需走 G4，而非 leave）。

### G2. 人数上限 + 候补名单 + 自动递补 — P1

- **场景**：一片场地双打 8~10 人最合适，多了上场太少；满员后仍有人想报名。
- **价值**：满员不拒绝、空位自动补，是约球最常见的排队诉求（球局掌等竞品的成熟功能）。
- **数据/思路**：activity `capacity`；player `state/waitlistSeq`；创建球局时可选填「人数上限」；join 页显示「正式 N/上限 M，候补 K 人」；leave 触发递补 + 订阅通知。
- **风险**：自动递补的通知依赖订阅消息模板（v1.15.1 遗留，需申请）；模板未就绪时降级为「候补者打开小程序看到已转正」。

### G3. 签到 / 到场核对，签到后才进轮转 — P1

- **场景**：开场前组织者问「谁来了」，手动数人；没来的人还挂在名单里，导致轮转表有人缺席。
- **价值**：名单与实际到场一致，**轮转直接基于到场者生成，对阵不再出现空位**；同时让 ELO 只结算真正上场的人，提升排位数据真实性。
- **数据/思路**：`checkInOpen` + player.`checkIn`；组织者一键开启签到，球友在 join 页「我到了」，组织者可代签；`rotation` 生成入口的选人列表默认勾选「signed 且 checkIn」，允许手动改。
- **风险**：单机/无云环境（组织者代登记）需保留「组织者一键全员签到」兜底；老球局无签到数据时默认全员到场，不影响历史。

### G4. 现场临时换人 / 弃权 — P2

- **场景**：已开赛有人受伤/早退，需要替换或判某场弃权。
- **价值**：覆盖现场异常，避免轮转表卡死。
- **数据/思路**：在已确认轮转上提供「标记弃权（按当前比分或 0:目标分记负）」「用候补/未上场者替换后续轮次」；仅作用于未记分场次，已确认结算的比赛不改（遵守 v1.14 锁定）。
- **风险**：替换会改变圆桌轮转的公平组合，建议只重排未开始的轮次（复用 rotation 算法对剩余人员重算），已完成轮次不动；实现较繁，置 P2。

### G5. 费用 AA / 记账（只记账，不碰在线支付） — P1

- **场景**：组织者垫付场地费，赛后按人头平摊、催缴费、记谁没给。
- **价值**：组织者每场必做的高频杂务；行动榜、球局掌均验证为刚需。
- **明确边界**：**MVP 不接微信支付**（需商户号/资质与结算合规，门槛高），只做「账单 + 缴费状态」，钱走群收款/转账，可附收款码图片或备注。
- **数据模型**：activity 新增
  ```
  fee: {
    total: Number,             // 总费用（元）
    rule: 'equal' | 'byAttendance',  // 按报名人数 / 按实际签到人数平摊
    note: String,
    collectorOpenid: String,   // 收款人（默认组织者）
    paid: [playerId 或 openid] // 已缴
  }
  ```
- **思路**：组织者录入总额与分摊方式 → 自动算每人应缴（byAttendance 用签到名单，最贴合实际）→ join 页球友看到「我应付 X 元 / 已缴」，组织者逐个标记已缴、一键复制「未缴名单 + 金额」到群。云函数 `setFee`（组织者）、`markPaid`（组织者）。
- **风险**：金额计算要在纯函数（可并入 `utils/signup.js` 或新建 `utils/fee.js`）里并单测（除不尽的尾差处理、请假/未签到不计）；不碰资金流，规避合规风险。

### G6. 场馆信息轻量增强（为地区榜预埋） — P2

- **现状**：已有 `venue`（场馆名）+ `courtText`（场地备注）纯文本。
- **功能**：创建球局时可选「发送位置」（`wx.chooseLocation`），存 `latitude/longitude/locationName`；结果页/分享卡显示场馆名，点击可导航。
- **价值**：现场找场地实用；同时为 v1.19 地区榜（按常打球位置推断城市/区）和未来场馆黄页低成本预埋地理数据，**不必现在就做地区归属表单**。
- **风险**：需在隐私指引声明位置信息；不做场馆数据库/预订（冷启动重，留 v2.0）。

### G7. 俱乐部 / 球队容器 — P1（独立成迭代，体量较大）

- **场景**：固定球友每周打球，需要一个「组织」把零散球局沉淀下来（羽聚时刻的主战场）。
- **价值**：留存与拉新的核心容器；俱乐部内部榜、队标、管理员权限、固定场馆/时间模板。
- **数据（概要，详细设计留待该迭代）**：新集合 `clubs {_openid(创建人),name,logo,createdAt}`、`club_members {clubId,openid,role}`；activity 增加 `clubId`；内部榜按 clubId 过滤 rank/activities。
- **风险/排序**：依赖报名状态机与个人主页基本成型，建议在 G1–G5 之后做，避免空中楼阁。

## 四、与排位 / 现有链路的关系

- **签到 → 轮转 → 确认 → ELO 形成更干净的数据链**：签到保证上场名单真实；轮转只用到场者；比分多方确认（v1.14）；超时兜底（v1.15.1）；ELO 结算（v1.15）。组织效率不是旁路功能，而是排位数据质量的上游闸门。
- **不改动 ELO 规则**：本期只改「谁进入轮转」，结算口径（confirmed 才计分、平分不计）保持不变。
- **订阅消息复用**：候补转正、签到提醒、催缴费都走 v1.15.1 的 `notify` 骨架，新增模板位 `waitlistPromote`、`checkIn`、`fee`；模板未申请前安全降级。
- **单机降级**：无云开发时，请假/签到/费用由组织者在本机操作（沿用现有单机模式），候补递补等协同能力仅云端可用。

## 七、本期 Top3 推荐

1. **报名状态机 + 球友自助请假（G1，含 G2/G3 的统一地基 `utils/signup.js`）**
   理由：当前球友只能报名不能取消、报名即占用名额，是约球最高频的「鸽子」乱象根源。先把 player 状态机（signed/waitlist/leave/checkIn）立起来，候补递补、签到、换人都建立在它之上，属于不可跳过的地基；纯函数可单测、云函数沿用现有鉴权，落地路径清晰。

2. **签到驱动轮转（G3）**
   理由：把「报名名单」和「实际上场名单」分开，轮转只排签到到场者，直接消灭「对阵表里有人缺席」的现场混乱，并让 ELO 只结算真实上场者，是组织效率反哺排位可信度的关键一环。

3. **费用 AA 记账（G5，明确不接在线支付）**
   理由：组织者每场必做、刚需且高频；只做账单与缴费状态、资金走群收款，可绕开微信支付商户资质门槛，低成本高满意度。按签到人数平摊（byAttendance）还与 G3 天然联动。
